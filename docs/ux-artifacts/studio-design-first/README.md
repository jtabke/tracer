## What the study is deciding

The current app mixes global tools, local representations, and current-versus-captured inspection. More controls cannot resolve that conceptual problem. The candidate organizes work around a stable engineering scope, with Graph/Table as representations of the same records and a single primary inspection state.

[Studio task design](studio-task-design.html) compares docked current-item context with a broader working canvas and detail below it. Both start on the same Graph scope. They share a full-width captured-input comparison because independent task review rejected the narrow docked comparison. The alternatives differ in current-item exploration, not the facts being inspected or a color treatment.

The proposed five areas are Project, Work, Evaluations, Configurations and Model. This is a recommendation to assess, not a requirement for five production routes. Graph/Table belong to a working scope rather than duplicate primary rail destinations. Project resumes recognizable engineering questions; Model explains configured development flow; Evaluations reads exact captured evidence; Configurations reads pinned revisions.

## Information hierarchy

| Information                                          | Primary presentation                               | Copy needed                                           |
| ---------------------------------------------------- | -------------------------------------------------- | ----------------------------------------------------- |
| Project and location                                 | Stable navigation and compact breadcrumb           | Recognizable project/area names                       |
| Current engineering scope                            | One scope header                                   | Starting key, meaningful title and actual bounds      |
| Branches, sibling/shared records, inputs and outputs | Directed spatial routes or aligned references      | Exact relationship meaning; no invented hierarchy     |
| Requirement/design content                           | Full statements in the active reading surface      | The obligation and assumptions are the work itself    |
| Captured/current difference                          | Paired revision columns, changed-field emphasis    | Values and reason for the recorded drift              |
| Result and human judgment                            | Separate outcome and review records                | Original outcome, rationale and scope of the judgment |
| Model definition                                     | Type workflow and selected connection/type context | Definition fields and exact native meaning            |
| Identity/provenance/history                          | Purposeful secondary detail                        | Exact technical records when relevant                 |

Frequently used representations and scope controls remain visible while they affect the displayed work. Graph/Table/depth disappear during a focused comparison because their work area is no longer displayed. Reading, editing and capture inspection are explicit modes rather than a stack of duplicate panels. Geometry must make input/output meaning understandable; labels supply meaning that geometry cannot encode.

## What the independent reviews rejected

The first study was not accepted unchanged. [Customer task review](../team-review/design-study-task-review.md), [design engineering](../team-review/design-review.md), and [QA](../team-review/qa-review.md) found narrow comparisons, evidence disappearing during judgment, duplicated statements and configuration fields, missing finding continuation, inconsistent depth, ambiguous model routes and preview state defects. Those findings caused a composition revision before any production integration. The independent [product recommendation](../team-review/studio-product-design.md) challenges the whole information architecture.

The revised study repairs those bounded issues. It remains a proposal. AI task simulation is not a human customer study; passing interaction checks is not owner design acceptance.

The fresh [independent product-manager gate](../team-review/product-design-gate.md) explicitly rejects treating inspector-placement alternatives as a settled whole-app design. It identifies missing author/connect entry, project/library/search context, advanced representations, full workflow vocabulary and interrupted/failed evidence states. Those findings are acceptance boundaries, not suggestions to add more controls immediately.

Fresh QA checks both variants after revision: native-hop excerpt scope and complete Table references, keyed preview edits/versions, judgment retained beside unchanged outcome, one shared model-label draft with Cancel, pointer navigation, and narrow capture return. The initial unhandled-input/state-echo defect was repaired before those distinct-value checks passed. The final parent pointer/review check is; screenshot inspection includes and. These validate the limited study's interactions and pixels, not the missing whole-product journeys.
