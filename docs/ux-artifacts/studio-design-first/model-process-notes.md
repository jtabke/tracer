# Orbit process-model study

**Status:** inspectable design proposal. No production application, native database, project schema or existing records were changed. This is not an execution system or an industry lifecycle prescription.

The study uses the complete Orbit schema from `examples/integrated-product-example.ts`, enriched by `exampleWorkflow(..., "integrated")` from `src/core/workflow-presets.ts`: **16 types, 15 native relationship definitions and 28 explicitly authored workflow routes**. The embedded data is derived from those modules. Native source/target constraints and workflow direction remain separate and inspectable.

The Overview groups types into Intent, Engineering, Exploration, Build & evidence, and Review & release. **Those groups are a presentation proposal**, not persisted stages, gates, approval rules or an ordered project process. Every type appears once. All 28 paths are drawn as context at desktop width; paths touching the selected type receive emphasis. Labels and individual semantics are read in the Inputs and outputs view, avoiding tiny text on the full map.

Evaluation focus exposes its five authored inputs: target acceptance criteria, requirement acceptance criteria, design under test, interface criteria and configuration under test. Its three outputs connect to findings, change assessment and decision feedback. Self-dependencies have an explicit return control. A selected route exposes both its development-flow meaning and its canonical native trace direction. Reverse workflow metadata never reverses a stored link.

At narrow width, the Overview becomes a readable type index grouped by the same presentation proposal. Input/output focus uses external buses: the five input cards are parallel contributions to Evaluation, not an invented serial chain through each other. Full names and labels stay at readable sizes; no fixed wide SVG is scaled down.

Configure has one local native-shaped schema draft. Visual mode edits existing type fields, adds a field, and edits a selected relationship's workflow label, direction, feedback and permitted endpoint sets. Text mode exposes that same schema as JSON. Invalid JSON is retained and blocks saving or switching to Visual; a simulated newer model revision demonstrates retained-draft conflict handling. Cancel restores the last saved preview model. Saving and version changes are **local study behavior**, not application commands or a claimed replacement for the canonical validator/concurrency engine. Preview validation covers the demonstrated type/field/workflow changes; native integration requires the existing complete guarded command path.

N8n informs the direct relationship inspection and input/output orientation. Its execution semantics are not applied to engineering information types. No n8n artwork or package is copied.

The browser walkthrough at 1024 px verified all sixteen type names, eight Evaluation focus routes, adding an optional numeric `duration_seconds` field, carrying the field into Text, retained invalid JSON, blocked invalid save/Visual switch, simulated stale version, retained conflict draft and cancellation. A workflow-label edit carried to Text while its native Design → Evaluation endpoints remained unchanged; cancellation restored the original label. The 390 px focus had eight routes and a 358 px iframe/document width with no horizontal overflow. The final walkthrough had no console errors. These are design-study checks, not owner usability acceptance, native persistence or backend regression evidence.

Open design questions: whether the overview grouping helps explain a real model, whether the gutter routes remain distinguishable for an edited/denser schema, whether the focused definition stage is preferable to a desktop dock, and whether narrow Overview should start with a selected-type focus rather than the complete index. These should be judged before application integration. The study does not yet offer drag-to-add relationships, node-arrangement persistence, importing schemas, native migrations or execution/gate enforcement.

## Focused definition revision

The independent PM critique identified the structural problem of properties below the full diagram, especially on narrow screens. Selecting a workflow path or opening a Type definition now enters a dedicated definition stage at **all widths**. Its primary heading names the selected type or directed path; the compact reference retains the originating type/view and authored meaning. A visible named Return restores the same flow, selected type and path, keeping its local draft. Configure gives that definition the primary area, with one Visual/Text draft and one Save/Cancel owner. The diagram is not stacked above the fields. Entering the stage focuses its native Return control; returning focuses the retained representation control. This is stage navigation, not a scroll jump to properties below a diagram.

## Consolidated studio proposal

The current proposal is now **`studio-complete-journeys.html`**, rather than two companion applications. The standalone Model file above is historical design evidence. The consolidated preview is `http://127.0.0.1:4352/`, renderer session `16236`, verified source SHA-256 `d7a49cc32c54dc4071dcff22dbaeb6bae992837de453b311f55abc45a4565721`.

Model uses the existing project rail, example picker, main area and footer. There is one Tracer brand, one main area and one parent widget-state writer/origin handler. The previous renderer/editor is reused as a retained per-project surface, rather than a new page shell or another standalone study. Its source is each active fixture's actual schema: **medical 18 types / 17 native relationship definitions / 22 authored workflow routes; technology 17 / 21 / 16; integrated 16 / 15 / 28**. Domain-specific groups are expressly presentation groups; types not covered by those proposed groups appear under Other project types. Types without authored workflow metadata stay visible with zero authored routes instead of receiving invented process connections.

Overview → inputs/outputs → selected definition → Configure → Visual/Text → retained flow all occur within that shell. Per-project model drafts, including invalid Text, remain in local memory across area and project changes. A Model Draft marker makes the retained definition draft visible while working elsewhere. The existing Return to unsaved draft action continues to resume an independent Work item/link/review draft; its project-switch guard remains unchanged. Model commands are isolated by the event's composed path, so a local definition rerender cannot accidentally invoke the parent Graph or Work command owner.

**Save definition rehearsal** commits only the local model rehearsal. It does not migrate project records, replace the fixture schema used by Work forms, alter permitted Work connections, or call any backend. That distinction and the reload limitation are explicit in the Model footer. Full model schemas are intentionally excluded from the existing bounded widget-state snapshot. Native model saving must eventually use the guarded canonical schema command and reconcile Work against the new schema; this proposal does not pretend that integration exists.
