# Tracer application-shell study

**Status: owner review pending.** This is a dark-default, browser-memory study of the whole Tracer shell. It does not change the production UI or write project data.

The project picker switches between two isolated study datasets: Orbit R1 and Aster Home BP. Each page retains its own session-only working state. This demonstrates project switching in the shell; it does not select or combine SQLite files. The running Tracer server still opens one configured project database per launch.

[Open the application shell](shell.html#overview). Overview is the default entry point, with project counts and a connected data-model graph as the primary surface. Each type has one canonical node and arrows show authored relationship directions. Selecting a node opens its actual item collection; Project model opens the complete schema in a graph editor. The retained DES-01 requirement scope works as Table, Document, and Graph while preserving selection and inspector context. The local toolbar creates independent requirements and connects existing or session-created requirements; the inspector edits the selected record. These actions remain local to the browser tab; project switching and page reload retain each project’s separate study state through tab-scoped session storage. Closing the inspector shows the unobstructed working surface.

Orbit now uses **one coherent native export: 71 records, 174 connections, 16 types, 20 relationship types, six evaluation activities, four recorded outcomes and three captures**. Its four explicit intent relationships preserve shared functions and requirements. Architecture, interfaces, experiments, findings and product choices remain distinct from Aster's medical model. Criterion scope and examination of a design are separate relationships; no activity or connection alone establishes execution. Current evaluation definitions contain method/purpose; receipts preserve exact original v1 simulated reports and declared inputs. Three receipts capture DES-01 v1 while the current design is v2; the shared-power result does not declare that firmware as an input. Acoustic and schedule activities have no result.

The selected baseline has 15 item/24 relationship pins, option B has 10/14, and the distinct firmware-v2 follow-up has 5/4. Selection records do not duplicate native pin manifests or claim a physical assembled build. The follow-up still uses the starting selection record as subject; its own capture identity and actual members determine its versions. The [clean Orbit definition](clean-orbit-model.ts) and [native generator](generate-clean-orbit.ts) reproduce the candidate in a new directory. The shared runtime uses the `orbit-clean-v1` namespace; earlier Orbit drafts stay in `tracer-study:orbit`.

[Open Aster Home BP](medical.html). The current medical candidate uses an isolated native fixture: **99 records, 219 connections, 13 types, 15 relationship types, eight verification receipts and one configuration capture**. The capture contains 29 exact item pins and 62 relationship pins. Current scope starts with DEV-01's five user needs and their actual PRS obligations and validation plans. Four validation plans have no execution. RUN-01 retains PRS-02 v1 while the current requirement is v2; other seven comparisons are current.

Dependency cleanup retains the 60 actual hierarchy links, removes 11 generic parent implementation rollups and two unsupported direct mappings, and leaves 19 scoped direct contributions. Supervisor Stop transitions and storage time-validity remain direct partial contributions; they do not implement child debounce or clock initialization. The item inspector shows exact calculated allocation paths separately from recorded implementation. Five scoped design dependencies identify real prerequisites; 36 verification links name planned criteria without inheriting parent coverage. Debounce, clock initialization and profile-ID representation gaps remain visible rather than gaining invented artifacts or test results. Related protocol receipts disclose whether the selected item was a declared captured input.

Cleanup appends native link revisions and removals in a copy of the original isolated fixture. All item IDs and fields, eight receipts and the full capture stay identical. Captured connections retain their original pinned fields and show whether the current connection is unchanged, updated or removed. The [cleanup command](cleanup-medical-fixture.ts) refuses existing destinations; the [link corrections](medical-link-cleanup.ts) are shared with the fresh generator, which captures the old baseline before applying corrections.

This study checks local draft structure, not the server's complete schema migration, coverage or captured-version save contract. Unknown schema properties and coverage expectations are preserved.
