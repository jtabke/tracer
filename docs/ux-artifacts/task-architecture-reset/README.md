# Tracer task-architecture reset

**Status: both compositions rejected by the owner.** The owner finds their decorative eyebrows, repeated information and hierarchy unlike a useful real application, with unclear purpose/actions. Preserve these fictional Orbit/Aster studies as historical mechanics and semantic evidence; they are not candidate production compositions or design acceptance. Replacement exploration follows the owner's actual Excalidraw references under `../task-surface-reset/`.

The benchmark question is:

> What does the DES-01 duty-profile change put into question across pickup, energy, thermal, timing and acoustics?

This is the question a proxy reviewer actually tried to answer in the integrated application. The current five family modes made the reviewer translate view names, native relationship direction and inspector boundaries before reaching result freshness. Table and Coverage converged on nearly the same comparison after repair; Reading and Relationships repeated content already present in the row or inspector. The DES-01 inspector's output-scoped “Captured results” section was literally correct but answered the wrong question: the relevant receipts captured DES-01 as an **input**.

The alternatives therefore challenge the page and mode structure rather than preserve it.

**Cross-industry challenge:** the literal Orbit board is not a reusable production design. Fresh [fixture reads](cross-industry-read-audit.json) find zero receipts directly on Aster/Gatherline check definitions, although their explicit definition-to-run routes reach actual stored receipts. Aster's focused component is not a declared input of those results; Gatherline can have a current focused input while another declared input changes. The recommendation is therefore conditional on a generic scope-first context with project-authored ordered result routes and complete create/connect/review stages. The [prospective interaction contract](implementation-contract.md), [read feasibility](read-contract.md) and [QA cases](read-contract-qa.md) own those requirements. They remain unselected; the screenshots illustrate Orbit's read composition plus client-memory author/connect rehearsals in the Orbit and Aster fixtures.

## Alternative A — contribution board (recommended)

[Open the interactive source](contribution-board.html#work)

The product enters through a retained engineering question. One readable row surface combines:

- the five obligations connected to DES-01 through recorded `realized_by` links;
- each obligation's other recorded design contributions;
- the explicit result route from each row to its terminal output;
- whether each reached terminal output has immutable receipts;
- whether that exact receipt captured DES-01;
- current drift and review state, kept separate from the immutable outcome.

The row does not say a requirement is verified. In Orbit's configured one-step route, EVAL-R01 is both the linked evaluation and terminal receipt output. Its receipt captured DES-01 v1, but REQ-R01 itself is not a declared input. That distinction is visible in the row. Other projects may reach a run output only after an explicit definition-to-run step; the board must never look for receipts on the first definition by default.

The complete task path shown is:

1. Resume the human question from Project.
2. Compare all five obligations without selecting Table, Coverage, Relationships or Reading.
3. Select REQ-R03 and open the exact EVAL-R02 receipt.
4. Compare captured DES-01 v1 with current v2.
5. Return by name to the selected energy-obligation row, with its selection and reading position retained.

The same study now makes the missing author/connect architecture inspectable:

1. Use the DES-01 scope header to **Create requirement** or inspect bounded existing candidates before creating.
2. Author the actual Orbit requirement fields, interrupt and resume the single retained draft, then save a hypothetical `REQ-P01` item **without a connection**.
3. Review the exact incoming proposal `REQ-P01 → realized_by → DES-01`, including required `scope`, `source_version` and `review` relationship fields.
4. Record that proposal only in browser memory and return by name to **Related requirements for DES-01**. The proposal is visibly outside the complete five-row fixture read and creates no evidence or readiness state.

Existing-candidate selection shows the full current statement, status, owner and recorded contribution context before preparing the same connection review. “Not connected here” is a scope fact, not a suitability recommendation. The receipt path exposes the exact captured output fields and local recorded-field disclosures for all five inputs before the canonical judgment choices and required rationale. A paused EVAL-R02 review resumes with its expanded receipt context and draft intact while the immutable outcome remains unchanged.

Compare is the primary working surface. Map is an optional lens over the same retained scope and selection; it is no longer a peer task mode. Full statements remain in the rows. Only the named create/connect/review rehearsal is wired. Other production capabilities are visibly disabled or labeled outside this study.

This is the recommended architecture because it supports the frequent author/connector task and the observed review question without requiring a persisted change assessment. It can also support new-design completeness work while preserving truthful absence semantics.

## Alternative B — recorded assessment dossier

[Open the interactive source](change-dossier.html#evidence)

This is a distinct, guided flow for an existing `CHG-R01` record:

1. Read the DES-01 item revision v1 → v2.
2. Review the ten subjects explicitly referenced by CHG-R01.
3. Reassess evidence that either appears in that subject list or has an immutable receipt that captured DES-01 v1.
4. Record a review for one exact receipt.

The dossier keeps two reasons for attention separate. EVAL-R02 is both an explicit assessment subject and a receipt dependency. EVAL-R01 and EVAL-R03 are outside the assessment list and appear because their receipts captured DES-01 v1; EVAL-R01 remains inspectable even though REQ-R01 was not a declared receipt input. EVAL-R05 is a definition with no result. REQ-R05 has no recorded evaluation link. EVAL-R04 is excluded because its receipt does not capture DES-01.

This alternative does **not** show project “before” versus “current” impact. The Orbit fixture has no named project baseline for the change. It shows one entity's revision history plus recorded assessment subjects and receipt comparisons. Recording a receipt review does not approve or close CHG-R01. A true baseline-impact dossier would be a separate capability and must require a named baseline rather than reconstruct one from nearby revisions.

The dossier is useful when a project already records a change assessment. It is a weaker default architecture because new-design work and ordinary relationship authoring would have to enter another structure, and the fixture cannot support a whole-project before/after claim.

## Illustrated Orbit read contract

The current UI cannot compose the illustrated row truth from one existing projection. `WorkspaceReceipts` queries receipts where the selected item is the **output**, which is why DES-01 says it has no captured result. For this specific Orbit scope, a server-owned bounded composition would:

1. Read the complete or explicitly paged obligation family for incoming `realized_by` links to DES-01.
2. For each obligation, read the recorded steps of its explicitly configured context and result routes.
3. Resolve each selected ordered result route to its declared terminal output. For Orbit, `evaluated_by` reaches the evaluation output in one step; Aster and Gatherline continue from a definition to a run. Query immutable receipts by reached terminal output and return exact availability/count.
4. For every returned receipt, disclose whether its declared dependency set includes DES-01. A result that did not capture DES-01 remains visible as unmatched context; it must not be hidden and turned into an apparent “no result” state.
5. Where DES-01 is a declared input, compare that exact capture with the current native record and report changed/current/unknown separately from outcome and review.
6. Allow an intentional “captured DES-01” filter only while retaining the unmatched-result count and a route to those receipts.
7. Return exact scope/page completeness, output-receipt counts, root-dependency counts and stable receipt identities. Do not silently choose the newest receipt as the valid one when several exist.

This illustrates the required semantic distinctions, not a generic direct-definition lookup. Other projects require explicitly selected routes to terminal result outputs. The [prospective read contract](read-contract.md) maps those routes and existing owners; no new projection is implemented. A client must not join several independently changing reads and imply a consistent snapshot.

## Evaluation

| Criterion                            | A — contribution board                                                           | B — recorded assessment dossier                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Starts from the user's question      | Strong: the saved/resumed object is the question and scope                       | Strong only when a recorded change assessment already exists                          |
| Supports daily author/connector work | Strong: edit/connect stay in rows and selected detail                            | Weak: guided review steps subordinate authoring                                       |
| Makes result freshness visible       | Strong: per terminal output reached by the selected route                        | Strong: evidence worklist is the core step                                            |
| Preserves semantic distinctions      | Strong if the new bounded contract is implemented                                | Strong; explicit subject, captured dependency and missing link are labeled separately |
| Avoids inferred readiness            | Yes                                                                              | Yes                                                                                   |
| Works for new design                 | Yes, with project-declared expectations where available                          | No; it assumes a change-assessment record                                             |
| Works for sustaining change          | Yes for shared-contribution questions; optional Map supports route exploration   | Yes for the bounded recorded-assessment and receipt-review task                       |
| Mobile composition                   | Rows stack as obligation → contributions → check; no horizontal comparison table | Four steps become a compact 2×2 navigator; evidence cards and exact review stack      |
| Main implementation risk             | Requires a consistent row + ordered-route + terminal-output composition          | Can be mistaken for full baseline impact or overall change approval                   |

Recommendation: choose A as the next complete thin journey. Keep B as a separate recorded-assessment task, and do not position it as project baseline impact until a named baseline exists. This recommendation should be reviewed with the owner before replacing production navigation.

At narrow widths, exact-result return must restore the selected obligation and its scroll position. The study also adds a compact five-obligation jump strip so users can scan pickup, energy, thermal, timing and acoustics without walking the entire stacked comparison. This is navigation within the retained question, not another representation mode.

The independent product critique is recorded in [task-architecture-product.md](../team-review/task-architecture-product.md). It reaches the same recommendation and documents the exact receipt-dependency limits.

## Inspectable states

### Cross-industry authoring stress test

[Open the Aster authoring study](medical-authoring.html#board). This applies the same Alternative A board and task ownership to the fictional medical-device fixture; it does not add a medical-specific workflow or select the architecture for production.

Two cases test whether the composition survives domain change:

1. **PRS-14 truthful zero** shows a complete scope with no recorded outgoing subsystem allocations. “Create subsystem requirement” remains an explicitly optional, user-chosen mechanics probe. The board does not infer that clinical decomposition is required, that the project is empty, or that the stated clinical-plan gap is satisfied by a subsystem child.
2. **PRS-02 add requirement** keeps both canonical allocations and their full statements visible before create/connect. It is a narrow mechanics rehearsal after the user has chosen an additive path; revising SYS-02 is also plausible work and remains outside this study. Existing relationship `source_version: 1` is shown as project-owned recorded metadata beside the current parent revision v2; the study makes no automatic stale or validity judgment from the number difference.

Both paths use the captured `subsystem_requirement` schema, save a hypothetical record without connections, review the exact stored direction `PRS → decomposes_into → subsystem_requirement`, expose all required relationship fields, and return by the parent name. Each created record gets a distinct client-session study identity; the prototype does not invent or allocate a project key. A saved item can be paused, connected, or finished and kept visibly unlinked; finishing releases the single active task owner without requiring a connection. Finished unlinked items remain available for optional connection while independent create/connect work can begin in either case. Completed linked and unlinked study records appear outside the canonical fixture rows and never change their count. The representative existing-candidate page discloses that 5 of 15 compatible records are loaded, disables the exact PRS-02/SYS-01 and PRS-02/SYS-02 pairs, and describes other schema-compatible items without endorsing their engineering suitability.

The stress test supports the Alternative A hypothesis: one board and one item/connection task owner can express both a zero-member scope and a many-member add-requirement task without changing the core information architecture. It remains a conditional design finding until owner selection and production verification; it is not implementation approval.
