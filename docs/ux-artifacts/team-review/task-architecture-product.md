# Product review: task architecture

Status: independent AI product recommendation, October 13, 2026. These alternatives are not a selected replacement design or owner acceptance. Orbit content is fictional; the walkthrough is read-only task evidence, not human usability research.

## Question and current friction

“Which recorded obligations need reconsideration after the shared DES-01 firmware design changed?”

The isolated Orbit workspace provides five useful obligation rows and explicit design/evaluation columns. It also exposes five peer representations, a long relationship-scope selector, permitted-column choices and a competing root inspector before answering the question. The inspector's output-scoped “No captured result” statement is literally correct for DES-01 but unhelpful here: relevant receipts capture DES-01 as an input. Repeating obligation → evaluation definition → captured result detours makes the engineer reconstruct the answer.

This recommendation follows [PN-03/04/07/09 and UR-23](../../user-needs.md), the [complete task contract](../studio-design-first/complete-task-contract.md) and the owner's instruction to challenge designs/features rather than only polish them. Existing screen boundaries and passing tests do not establish task fit.

This is design inference from recorded reference evidence, not competitor usability testing or approval to inherit their ontology/process.

## Cull or subordinate

- Merge duplicate Table/Coverage destinations into one readable row surface. Display choices must not create another task boundary.
- Absorb Reading into rows and contextual detail. Relationships and Graph remain optional perspectives when they answer a particular question.
- Replace definition-first receipt detours with a relevant captured-result summary and direct opening of the existing single receipt-review destination.
- Subordinate technical scope construction, permitted-column inventories, raw metadata and capture catalogues to deliberate controls. Do not require source/query setup before inspecting recorded evidence.
- Challenge Evaluations/Configurations as daily peer destinations; preserve their catalogue/creation capabilities where a task needs them.

Preserve direct edit/connect, full statements, keyboard access, version guards, drafts, bounded-read disclosure and saved-view compatibility. Culling redundant UI is not permission to silently remove useful operations or stored scopes. An allowed relationship slot is not automatically a mandatory completeness expectation.

EVAL-R04 is a failed shared-power evaluation capturing REQ-R06, IF-01, DES-04, DES-05 and BUILD-R01. It does not directly capture DES-01. It can appear as explicitly connected context, never as automatic firmware-input drift or a timing evaluation.

Show recorded relationship, exact captured-input dependency, recorded outcome, current comparison and review judgment separately. Avoid aggregate “verified,” “safe” or automatically assigned “needs reassessment” labels. Missing links, missing receipts, failed reads and unknown inputs are different states. Absence of a modeled path does not prove absence of impact.

## Required acceptance journey and capability limits

Use an isolated fixture for writes. Open the shared firmware-change question, explain the five rows' differing evidence situations, open EVAL-R02's receipt directly, inspect DES-01 v1 versus v2 and the complete declared input set, record a rationale with the existing comparison guard, then return to the same scope/selection. The original outcome remains immutable. The judgment applies to that disclosed receipt comparison, not the whole obligation set or product.

Also demonstrate cancellation, retained drafts during context inspection, conflict/changed-comparison recovery, unavailable reads, keyboard focus return and a narrow layout that retains the question and row/result distinction. Reload must show confirmed writes; no draft recovery across reload is implied. A successful walkthrough and green checks do not establish human usefulness or owner visual acceptance.

Native family/connection reads, historical input snapshots, receipt comparison and guarded receipt reviews support the basic journey. A compact cross-row evidence summary still needs bounded composition over explicit linked evaluations and their actual receipts; the current output-scoped root receipt list cannot answer the input-dependency question. It must not silently infer relevance or completeness from filenames/type permissions, truncate while claiming completeness, or select the latest receipt as automatically authoritative.

The core change-impact contract supports B through a named baseline, explicit relationship types/direction/depth and captured dependency discovery. Its baseline selection and investigation UI are not delivered. Do not fabricate a baseline from a receipt or add a persisted proposal/readiness engine. Missing timing/acoustic work remains a human engineering question, with ordinary contextual author/connect actions where appropriate.
