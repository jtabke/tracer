3. **Completing and resuming work:** decide the preferred create → proposed connection → saved scope sequence and how a user consults full sibling content while retaining the draft. The new composition makes these reviewable; a successful preview save is not the design decision itself.
4. **Review applicability and recovery:** inspect more than one changed input, an unavailable input, a relevant comparison refresh and the paused-review return. Their technical receipts can support review, but this rereview did not independently exercise every recovery state or all three authoring domains.
5. **Owner composition acceptance:** present the complete small tasks now. Avoid another open-ended control-polish cycle before that review. Technical QA, this PM disposition and simulated customer critique remain separate evidence.

No new stylistic optimization is needed to decide those questions. The primary mode and route hierarchy are now concrete enough for a meaningful owner walkthrough.

## Judgment

**The direction is more coherent; the application design is still not ready for native integration.** Actual project vocabulary and complete records make this a substantially better assumption test than the prepared five-node excerpt. The stable project areas, visible local representations, explicit preview boundary and retained scope remain strong candidates.

However, the content hierarchy still treats the current neighborhood as the dominant surface even when the user's job has changed to authoring or reviewing a definition. The next work should settle that mode transition and the meaning of a purposeful engineering scope. More controls, tighter row spacing or automatic scrolling would not resolve those conceptual problems.

## Highest-value changes before optimization

### 1. Define a purposeful scope before choosing its representation

The Aster pressure scope immediately includes user need, allocations, risk control, DHF review, change record and two build records. Those are valid recorded connections, but “all relationships within N hops” is an investigation neighborhood, not the same thing as the question “Does the old pressure evidence support the expanded range?” Document and configuration hubs quickly dominate the neighborhood at greater depth.

An authored scope should name its engineering question and the relevant relationship recipe or subject set. Broader recorded context must remain available with an explicit scope change and honest counts. Custom scope editing should use actual project relationship names, not a fixed medical tree. A selected recipe is not “full trace”; a shortest path is not engineering impact.

The parent proposes named project-specific relationship sets with Custom editing and an accessible All relationships option. That is an appropriate next design experiment **if the active set, excluded meanings and bounded counts are explicit**. It must not quietly redefine an existing scope or hide a shared identity to make a diagram attractive.

### 2. Give authoring the primary work area

At 1440 × 1000, five full-statement rows occupy roughly the first 700px of the Aster scope. Edit/Connect/History begin below them. Create inserts its draft below the same list. The user has changed from reading the neighborhood to writing a requirement, while the composition continues to prioritize the neighborhood.

Adopt an explicit read → author arrangement: the draft becomes the dominant readable surface, with compact parent statement and sibling context available alongside or above it. Save/Cancel and draft identity belong to that surface. Graph/Table can remain reachable for contextual inspection while preserving the draft; they should not leave the active authoring task beneath a long census.

The inspected “Under SYS-07” wording also implies a relationship before one has been recorded. Use “In context of SYS-07” until a named source/relationship/target proposal is reviewed. A saved unlinked item and a completed allocation are different outcomes.

### 3. Make Trace a relationship recipe, not a type register

Recommended Aster example: **PRS → decomposes_into → SYS → realized_by → OUT → verified_by → VER → executed_as → RUN**. Use aligned columns whose headings carry exact relationship meaning and direction. Show sibling branches, empty intermediate slots, common prefixes and shared identities recognizably.

Selecting a protocol must also expose its other actual criteria and design inputs together. Direct PRS → VER remains reachable and visibly distinct from the long design path; it must not eliminate the design merely because it is fewer hops. Graph remains the arbitrary loaded topology. Trace becomes deliberate route reading, with its selected recipe and limits disclosed.

The representation choices need clear jobs: Table for comparing/editing scoped attributes, Reading for full statements, Graph for connected topology, Trace for a declared multilevel relationship route, and Matrix for a specific pairwise mapping question. Visible buttons alone do not establish that users understand the choice.

### 4. Lead evidence review with the question and actual difference

The customer report establishes a clearer captured/current comparison and preserved evidence during judgment. Retain that structure. The primary object is the captured **result against a disclosed current input comparison**, not an isolated changed item.

Keep a compact complete input-state summary and selectable changed/unknown/matching inputs near the main comparison. A long full-width input list must not push the actual changed statement below the first useful review viewport. Nor should compacting the list hide another changed or unknown input. Outcome, captured configuration, drift and human judgment remain separate facts.

The parent proposes a compact all-input selector beside the primary difference. Review that with one missing/unknown input and more than one changed input before treating the single changed Aster record as acceptance.

### 5. Connect the application Model entry to one real model experience

The full Orbit Model study is a substantial advance. Sixteen types and 28 authored paths establish actual vocabulary and branching. The Evaluation input/output focus clearly distinguishes target/requirement/interface criteria, design under test and configuration under test. Selecting Design exposes one connection definition, including native meaning and authored display direction. These satisfy a meaningful part of the owner's conceptual correction.

The Work application's earlier focused type-card presentation is not a substitute for this experience. Provide an explicit transition to the full visual model and Configure journey; avoid maintaining two competing pseudo-models. A temporary external study link must be labeled as a study, with its return and limitations clear.

The overview is useful orientation, but its unlabeled highlighted routes and repeated authored-path counts do not by themselves explain development. Its selected focus is where meaning becomes readable. A count is secondary to “what feeds this type and what leaves it.” Review the intended overview → selected path → configuration sequence as one journey, not separate screenshots.

## Narrow layout and definition editing

At 390 × 844 in Configure, several header/control rows and the stacked input cards fill the initial viewport. The selected Design → Evaluation properties are much farther below. This repeats the authoring hierarchy problem in a different task.

Selected definition editing should become an intentional readable stage at constrained width, with a visible return to the retained flow. The user must see which definition is selected and where edits are made without scrolling past all inputs and outputs. The exact desktop docked/focused treatment remains a choice to review; smaller type and additional scroll jumps are not a settled design.
