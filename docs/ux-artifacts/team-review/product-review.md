## What belongs visually versus in copy

- **Visual:** development inputs/outputs and feedback; exact direction; branching and shared identities; selected root and focus; active view; depth; current versus captured version differences; failed/changed/missing result states with readable labels.
- **Compact labels:** node key/type, edge meaning, depth and item/link totals, omitted scope, project/schema version where it governs a write, and the precise meaning of a result badge.
- **Supporting copy:** rationale, assumptions, detailed task teaching, the distinction between a recorded link and established realization, and recovery guidance. Place these next to the relevant action/result or in a dedicated example guide rather than repeating a generic caveat beneath every projection.
- **Details on demand:** UUIDs, raw fields, long dependency lists and revision events. Retaining these disclosures is compatible with exposing frequent controls.

## Design hierarchy recommendation

The shell answers “which project and task area?” The scoped header answers “which engineering item/question?” A single toolbar chooses representation and trace scope. The main working surface shows relationships and complete statements. The inspector answers the currently selected detail question. There should be one authoritative place for each of those jobs; a second surface must add a different perspective rather than repeat the first.

Existing documents still describe Advanced views as collapsed, and family Graph as an unexpanded read of the same family snapshot. Update their current-status paragraphs when the new controls and depth behavior are integrated; historical receipts should remain historical.
