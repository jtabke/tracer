# Tracer application visual reset

Status: owner rejects the application's overall layout and experience, including the type map and workspace home, while identifying Graph and Table as useful working interactions. The active owner goal is to design and implement a beautiful, intentional application. The owner selected **Project studio (recommended)** and its application implementation is now being verified. These two original compositions remain design studies; their interactions operate on an embedded snapshot of fictional Orbit data, not the project database.

The source is [tracer-directions.html](tracer-directions.html), an in-conversation comparison. It includes project home, shared-control table/graph, item inspection, local draft preview, searchable records, model connections, evaluation browsing and configuration browsing. Project studio gives the project a stable navigation rail and compact contextual workspaces. Focused workspace emphasizes a bounded reading surface and quieter top navigation. The comparison controls retain each composition's local state. They do not imply native persistence, configuration approval or a new readiness policy.

## Reference translation

- Carbon: stable application framing, purposeful graph/table switching, a scoped diagram and one adjacent detail region. Manufacturing genealogy does not imply requirement satisfaction.
- Notion: a bounded reading surface, strong content hierarchy and side-peek context. Keep engineering evidence and revision meaning explicit.
- Jama: selection stays visible beside its detail; avoid adopting the one-record-at-a-time limit reported by the owner.
- Tyler Lange: orderly tool hierarchy, aligned data and settings disclosed near the relevant working area. Avoid a permanent settings wall.
- Tyler Wain: an appropriately sized contextual control surface, rather than a toolbox occupying every task.
- Daniel Broughan: edits happen where attention already is, with clear save/cancel boundaries. Preserve native concurrency checks beneath that interaction.

The reference board retains source attribution and original pixels. This study contains original interface work, not copied source artwork.

## Implementation direction

Selected: **Project studio** for the application shell, borrowing the calmer reading/detail treatment from Focused workspace. Keep existing graph and relationship-table capabilities. The selected Family and trace outcome remains: readable siblings, explicit sharing, retained context and progressively disclosed evidence.

Start with shell, coherent project entry and shared navigation/visual tokens. Then replace the model knot with a focused connected reading layout and give Evidence a result-first entry. Reuse native commands, schema/version guards, bounded queries and immutable receipts/configurations. Project terminology remains configurable; Orbit labels and example scopes are data for this study, not universal application rules. Full statements must remain available together for sibling comparison; title-only presentation is an optional density choice, not a replacement requirement.

The owner selected Project studio in the inline response. Further visual feedback can still revise the implementation. An active implementation goal supplies authorization for the redesign, but technical checks and a polished study do not establish owner visual acceptance. Neither legacy page boundaries nor the cost of the current UI should constrain the replacement.

## Application implementation

- Persistent project identity/navigation and a bounded home using real guide tasks, saved views and project type counts. Ordinary projects show their own item index and useful empty/saved-view entry; no example tasks or activity are invented.
- All items retains the existing bounded browser. A family has local **Table / Graph** modes using the same root, selected identity and inspector draft; Graph can explicitly read deeper native traces. Relationships, Coverage and Reading remain available. Saved family recipes now support graph presentation as well as table/reading layouts.
- Readable statement/title hierarchy and quieter chrome; non-primary item properties are disclosed without creating another draft owner. History, technical identity, captures and evaluations stay reachable. Normal, wide and narrow layouts use different geometry instead of stretching prose.
- Project model is a visual workflow diagram. The overview shows all types and disclosed representative routes; type focus shows incoming → selected type → outgoing, including return paths and self loops. Selecting a connection isolates its explicit alternatives. Visual source/target picking creates a guarded, named new relationship rule; actual item links remain in recorded connection/workspace inspection. Any/None constraints stay in detail instead of becoming invented lines.
- Evaluations begins with actual captured output/outcome records. Clicking a result focuses comparison; creation and external observation use explicit disclosures. Outcome, drift and review remain separate. Configurations provides a dedicated paged catalogue and existing guarded capture flow.
- Existing general Graph/Table/Matrix and item editor remain in the visible Working views group. Native commands, write recovery, temporal restrictions, explicit bounds and mounted drafts remain. No new source integration, automatic impact or readiness policy is implied.

Current screenshots and browser receipts are recorded in [checkpoint](../../checkpoint.md). Remaining product work includes a mobile detail stage, consolidated general-graph/trace history context, project naming for ordinary databases, and larger evidence catalogue paging. These are follow-up opportunities, not claims that the current implementation contains those capabilities.

## Critique after the owner's cleanup request

The owner asks for continued design critique: remove duplicated information, make controls intentional, use space efficiently, and decide what belongs in visual structure versus prose. Passing workflow tests is separate from these design judgments.

The first studio pass still repeated the guide in chrome, the sidebar and home; repeated the scope statement beside its inspector; exposed five peer layouts; repeated type labels inside already grouped rows; and left a mostly empty Model detail pane. Those are corrected. Example workspaces live on home and contextual navigation; prepared multi-level traces have one home entry. The scope statement is read/edited once in detail. All five local representations and primary scope controls are visible; optional long shortcut lists and raw metadata use deliberate adaptive disclosure. Find items has one global entry and focuses the search field. Model has one scope control, fields on demand and no empty default inspector. The owner subsequently corrected its text-heavy permission lanes; these are replaced by the visual workflow map below.

### Page hierarchy

1. The shell establishes project identity and location. It does not teach the engineering workflow on every page.
2. A page or workspace establishes one purpose and one focused object/scope. IDs and versions support that purpose at lower emphasis.
3. Working content dominates: sibling statements, the graph, selected result or captured configuration. Table/Graph modes sit beside the scope.
4. The selected record's statement and local editing come next. Connection, capture and evaluation detail is available in context.
5. Metadata, technical identities, provenance, setup and less-used layouts are deliberate disclosures.

Repeated trace references remain intentional: each represents a distinct recorded connection to one shared identity. The removed repetition was explanatory material, redundant controls and repeated labels without another role. Wide prose is bounded; diagrams/tables can use the remaining working area. Narrow layouts reflow, while deeper mobile detail navigation remains a follow-up opportunity.

## Correction: the model must be visual

**Owner evidence:** UR-17 explicitly asks to see the development workflow through linked inputs/outputs and loops. The text-lane cleanup improved reading but lost the central visual model. That was a concept defect, not something more spacing or typography could fix.

The replacement makes connections the working content. Readable type cards and directed routes communicate topology; source/target selection communicates creating a link. Relationship names retain their exact project meaning. Connection controls precede the diagram; fields, alternative constraints and actual recorded connections remain detail. The overview includes every type and a representative route for each explicitly constrained relationship family, with the displayed/total route count visible. Focusing a type provides a smaller incoming/selected/outgoing composition with one identity for bidirectional neighbors. Selecting a connection reveals its routes. On narrow screens a native picker replaces the connection-chip row, and the focused type is centered in a scrollable diagram.

The owner identified the earlier diagram's semantic error: native trace direction is not development flow. The current model explicitly separates the two. Authored workflow paths can display reverse flow without reversing native links; Intent feeds Requirement, design and requirement criteria independently feed Test, and feedback is deliberate. Fresh realistic examples define those paths; legacy project proposals require review/save. Named stages, gates and execution remain gaps. Configure Visual/Text share one captured draft, and whole-map Overview is distinct from readable Frame selection. [Team review](../team-review/README.md) records the independent product, design, simulated-customer and QA critique requested by the owner.

Visual linking opens a reviewable named source → target rule proposal and saves it through captured schema/version guards. Conflicts retain the proposal. Changing existing alternatives/fields remains in Configure model; actual item links remain distinct. Current screenshots and verification are recorded in the checkpoint. This is a reviewable native candidate, not a claim of owner visual acceptance.
